<H2>Summary</H2>

<Prose>
  ShardScript provides two task-like types in the <InlineCode>async</InlineCode> namespace:{' '}
  <InlineCode>Task</InlineCode> for void-returning asynchronous operations, and{' '}
  <InlineCode>ValueTask&lt;T&gt;</InlineCode> for operations that produce a typed result. Both
  implement the awaiter pattern (<InlineCode>IAsyncState</InlineCode>, <InlineCode>IAwaitable</InlineCode>,{' '}
  <InlineCode>IAwaiter</InlineCode>) and integrate with the libuv-based cooperative event loop. The
  <InlineCode>shard.async</InlineCode> library adds <InlineCode>TaskCompletionSource&lt;T&gt;</InlineCode>,
  which lets non-async code or native callbacks manually complete a <InlineCode>ValueTask&lt;T&gt;</InlineCode>.
</Prose>

<H2>Syntax</H2>

<Prose>
  An <InlineCode>async</InlineCode> method declares <InlineCode>Task</InlineCode> or{' '}
  <InlineCode>ValueTask&lt;T&gt;</InlineCode> as its return type. Inside the method body, use{' '}
  <InlineCode>await</InlineCode> to suspend until an awaitable completes. From synchronous entry points,
  use <InlineCode>Task.Wait(task)</InlineCode> or <InlineCode>ValueTask.Wait(task)</InlineCode> to pump
  the event loop until completion.
</Prose>

<CodeBlock
  code={`using stdio;
using async;

namespace demo;

public static async func DelayedHello() -> Task
{
    println("before delay");
    await Task.Delay(100);
    println("after delay");
}

public static func Main() -> void
{
    task: Task = DelayedHello();
    task.Wait();
    println("done");
}`}
  language="csharp"
  filename="task_basic.shard"
/>

<Prose>
  <InlineCode>ValueTask&lt;T&gt;</InlineCode> is declared with an explicit result type and returns a value
  with the ordinary <InlineCode>return</InlineCode> statement:
</Prose>

<CodeBlock
  code={`using stdio;
using async;

namespace demo;

public static async func FetchNumber() -> ValueTask<int>
{
    await Task.Delay(10);
    return 42;
}

public static func Main() -> void
{
    task: ValueTask<int> = FetchNumber();
    ValueTask.Wait(task);
    result: int = task.Result;
    println(result);
}`}
  language="csharp"
  filename="valuetask_basic.shard"
/>

<H2>Exceptions / Errors</H2>

<ul className="space-y-2 text-text-secondary">
  <Bullet>
    <strong className="text-text-primary">Faulted task on Wait()</strong> — If a task completes with{' '}
    <InlineCode>FAULTED</InlineCode> state, <InlineCode>Task.Wait</InlineCode> or{' '}
    <InlineCode>ValueTask.Wait</InlineCode> re-throws the captured exception in the calling frame.
  </Bullet>
  <Bullet>
    <strong className="text-text-primary">Faulted task on await</strong> — Awaiting a faulted task calls{' '}
    <InlineCode>GetResult()</InlineCode>, which raises the stored exception inside the async method so it
    can be caught with an ordinary <InlineCode>try</InlineCode>/<InlineCode>catch</InlineCode> block.
  </Bullet>
  <Bullet>
    <strong className="text-text-primary">Result before completion</strong> — Reading{' '}
    <InlineCode>ValueTask&lt;T&gt;.Result</InlineCode> while the task is still <InlineCode>PENDING</InlineCode>{' '}
    returns the default/uninitialized value for the field. Always call <InlineCode>Wait()</InlineCode>{' '}
    or <InlineCode>await</InlineCode> the task first.
  </Bullet>
  <Bullet>
    <strong className="text-text-primary">Type mismatch in async return</strong> — An{' '}
    <InlineCode>async</InlineCode> method must return <InlineCode>Task</InlineCode> or{' '}
    <InlineCode>ValueTask&lt;T&gt;</InlineCode>. Returning a plain value type or <InlineCode>void</InlineCode>{' '}
    from an <InlineCode>async</InlineCode> method fails semantic analysis.
  </Bullet>
  <Bullet>
    <strong className="text-text-primary">Missing using async</strong> — <InlineCode>Task</InlineCode>,{' '}
    <InlineCode>ValueTask&lt;T&gt;</InlineCode>, and <InlineCode>TaskCompletionSource&lt;T&gt;</InlineCode>{' '}
    live in the <InlineCode>async</InlineCode> namespace. Forgetting <InlineCode>using async;</InlineCode>{' '}
    produces an unresolved-type error.
  </Bullet>
</ul>

<H2>Remarks</H2>

<Prose>
  <strong>Self-awaiters.</strong> Both <InlineCode>Task</InlineCode> and{' '}
  <InlineCode>ValueTask&lt;T&gt;</InlineCode> implement <InlineCode>IAwaiter</InlineCode> directly.
  <InlineCode>GetAwaiter()</InlineCode> returns <InlineCode>this</InlineCode>, so an{' '}
  <InlineCode>await</InlineCode> expression does not allocate a separate awaiter object. This keeps the
  hot path allocation-free.
</Prose>

<Prose>
  <strong>Lifecycle and rooting.</strong> When an async method starts, the compiler-generated state machine
  factory allocates the task object and calls <InlineCode>InternalRoot</InlineCode>. Rooting increments the
  task’s reference count and registers it with the event loop, keeping the task alive across suspensions
  even if no script variable holds it. On completion, <InlineCode>Complete()</InlineCode> or{' '}
  <InlineCode>SetResult()</InlineCode> releases the frame owner, resumes the continuation, and unroots the
  task so it becomes eligible for garbage collection.
</Prose>

<Prose>
  <strong>States.</strong> The internal <InlineCode>_state</InlineCode> field uses three values:
</Prose>

<DocsTable
  headers={['State', 'Value', 'Meaning']}
  rows={[
    ['PENDING', '0', 'The operation has not finished.'],
    ['COMPLETED', '1', 'The operation finished successfully.'],
    ['FAULTED', '2', 'The operation finished with an exception stored in _exception.'],
  ]}
/>

<Prose>
  <strong>Fire-and-forget.</strong> <InlineCode>Task.Shoot(task)</InlineCode> explicitly releases the task’s
  frame owner and marks it as fire-and-forget. The task continues to run on the event loop but no longer
  keeps the caller’s frame alive. At VM shutdown, fire-and-forget tasks are halted cleanly. You can also
  discard the return value of an async call, which starts the task independently because the rooted task
  object survives on the event loop; however, <InlineCode>Task.Shoot</InlineCode> is the explicit, supported
  API for this pattern.
</Prose>

<Prose>
  <strong>Synchronous fast path.</strong> <InlineCode>ValueTask.FromResult&lt;T&gt;(value)</InlineCode>{' '}
  returns a task whose <InlineCode>IsCompleted</InlineCode> property is already <InlineCode>true</InlineCode>.
  When such a task is awaited, the compiler’s await sequence sees the completed flag and jumps straight to
  the resume segment without registering a continuation or returning to the event loop. Use this for cached
  values and trivial synchronous fallbacks inside async APIs.
</Prose>

<Prose>
  <strong>TaskCompletionSource&lt;T&gt;.</strong> This class, provided by the{' '}
  <InlineCode>shard.async</InlineCode> library rather than the core runtime, creates a{' '}
  <InlineCode>ValueTask&lt;T&gt;</InlineCode> that is completed manually. It is useful when native code,
  callbacks, or another thread must decide when an async operation finishes. Construct the source, expose
  its <InlineCode>Task</InlineCode> property to awaiters, and call <InlineCode>SetResult</InlineCode> or{' '}
  <InlineCode>SetException</InlineCode> to transition the task to <InlineCode>COMPLETED</InlineCode> or{' '}
  <InlineCode>FAULTED</InlineCode>.
</Prose>

<Callout tone="blue">
  <InlineCode>Task.Wait</InlineCode> and <InlineCode>ValueTask.Wait</InlineCode> are cooperative: they block
  the calling thread by repeatedly calling <InlineCode>EventLoop.RunOnce()</InlineCode>. Timers and I/O
  callbacks still drain on the same thread while the caller waits, so the VM remains responsive even though
  the synchronous entry point is stalled.
</Callout>

<Callout tone="amber" title="Task.WhenAll / Task.WhenAny not implemented">
  Combinators such as <InlineCode>Task.WhenAll</InlineCode> and <InlineCode>Task.WhenAny</InlineCode> are not
  currently part of the <InlineCode>async</InlineCode> namespace. To wait for multiple tasks, start them and
  call <InlineCode>Wait()</InlineCode> on each reference individually, or build a custom completion source
  that tracks the remaining count.
</Callout>

<H2>Examples</H2>

<Prose>
  <strong>Concurrent delays.</strong> Multiple <InlineCode>Task.Delay</InlineCode> calls can be started
  before any of them are awaited, allowing the timers to run concurrently on the event loop.
</Prose>

<CodeBlock
  code={`using stdio;
using async;

namespace demo;

public static func Main() -> void
{
    t1: Task = Task.Delay(100);
    t2: Task = Task.Delay(200);
    t3: Task = Task.Delay(50);

    t1.Wait();
    t2.Wait();
    t3.Wait();

    println("all delays done");
}`}
  language="csharp"
  filename="task_concurrent.shard"
/>

<Prose>
  <strong>ValueTask.FromResult for cached values.</strong> When a result is already known, create a
  synchronously completed task instead of spinning up an async state machine.
</Prose>

<CodeBlock
  code={`using stdio;
using async;

namespace demo;

public static func LookupCached(id: int) -> ValueTask<int>
{
    if (id == 1)
    {
        return ValueTask.FromResult<int>(99);
    }

    return FetchSlow(id);
}

public static async func FetchSlow(id: int) -> ValueTask<int>
{
    await Task.Delay(10);
    return id * 2;
}

public static func Main() -> void
{
    cached: ValueTask<int> = LookupCached(1);
    println(cached.IsCompleted); // true
    println(cached.Result);      // 99

    slow: ValueTask<int> = LookupCached(5);
    ValueTask.Wait(slow);
    println(slow.Result);        // 10
}`}
  language="csharp"
  filename="valuetask_fromresult.shard"
/>

<Prose>
  <strong>TaskCompletionSource with a delayed producer.</strong> The producer is an async method that
  completes the source after a delay; the consumer awaits the source’s task.
</Prose>

<CodeBlock
  code={`using stdio;
using async;

namespace demo;

public static async func CompleteAfterDelay(tcs: TaskCompletionSource<string>) -> Task
{
    await Task.Delay(50);
    tcs.SetResult("ready");
}

public static func Main() -> void
{
    tcs: TaskCompletionSource<string> = new TaskCompletionSource<string>();
    CompleteAfterDelay(tcs);

    task: ValueTask<string> = tcs.Task;
    ValueTask.Wait(task);
    println(task.Result); // ready
}`}
  language="csharp"
  filename="task_completion_source.shard"
/>

<Prose>
  <strong>Exception propagation.</strong> Exceptions thrown inside an async method are captured by the
  task and re-thrown when the task is awaited or waited on.
</Prose>

<CodeBlock
  code={`using stdio;
using async;

namespace demo;

public static async func FaultyDelay() -> Task
{
    await Task.Delay(10);
    throw new RuntimeException();
}

public static func Main() -> void
{
    try
    {
        Task.Wait(FaultyDelay());
        println("unreachable");
    }
    catch (ex: RuntimeException)
    {
        println("caught faulted task");
    }

    println("done");
}`}
  language="csharp"
  filename="task_exception.shard"
/>

<Prose>
  <strong>Catching exceptions inside an async method.</strong> Ordinary{' '}
  <InlineCode>try</InlineCode>/<InlineCode>catch</InlineCode> blocks work across await suspension points.
</Prose>

<CodeBlock
  code={`using stdio;
using async;

namespace demo;

public static async func FaultyDelay() -> Task
{
    await Task.Delay(10);
    throw new RuntimeException();
}

public static async func CaughtAwait() -> Task
{
    try
    {
        await FaultyDelay();
        println("after await"); // never reached
    }
    catch (ex: RuntimeException)
    {
        println("caught inside async");
    }
}

public static func Main() -> void
{
    Task.Wait(CaughtAwait());
    println("done");
}`}
  language="csharp"
  filename="task_caught_await.shard"
/>

<Prose>
  <strong>Fire-and-forget with Task.Shoot.</strong> The caller does not wait for the background task.
</Prose>

<CodeBlock
  code={`using stdio;
using async;

namespace demo;

public static async func Background() -> Task
{
    println("background start");
    await Task.Delay(100);
    println("background end");
}

public static func Main() -> void
{
    Task.Shoot(Background());
    println("main end");
}`}
  language="csharp"
  filename="task_shoot.shard"
/>

<Prose>
  <strong>Fire-and-forget with ValueTask&lt;T&gt;.</strong> Use the generic overload of{' '}
  <InlineCode>Task.Shoot</InlineCode> when the discarded task carries a result type.
</Prose>

<CodeBlock
  code={`using stdio;
using async;

namespace demo;

public static async func Background() -> ValueTask<int>
{
    println("background start");
    await Task.Delay(100);
    println("background end");
    return 42;
}

public static func Main() -> void
{
    Task.Shoot<int>(Background());
    println("main end");
}`}

<Prose>
  <strong>Common mistake: reading Result before waiting.</strong> The <InlineCode>Result</InlineCode>{' '}
  property is only meaningful after the task has left the <InlineCode>PENDING</InlineCode> state. The
  commented-out line below would read the default field value instead of the real result.
</Prose>

<CodeBlock
  code={`using stdio;
using async;

namespace demo;

public static async func GetValue() -> ValueTask<int>
{
    await Task.Delay(10);
    return 7;
}

public static func Main() -> void
{
    task: ValueTask<int> = GetValue();

    // BUG: do not read Result while the task is still pending.
    // result: int = task.Result;

    ValueTask.Wait(task);
    result: int = task.Result;
    println(result);
}`}
